## 2. v4 要解决的实际问题

核心交互链是：**找到资源 → 选择资源 → 查看详情和配置 → 验证变更 → 审查权限 → 提交 → 查看服务端回执或定位失败**。

这要求重组页面和组件。仅让菜单可点击、把同一种卡片换成新颜色，不能证明配置、扩展、渠道和运行追踪的工作流成立。

| 范围 | 当前 v3 | v4 目标 |
| --- | --- | --- |
| 导航 | 17 个主入口，认知、关系、媒介、追踪等独立 | 13 个主入口，资源管理与标签子工作区 |
| 框架 | 深紫侧栏 256/76px、顶栏 72px | 浅色侧栏 230px、顶栏 62px、底部状态栏 26px |
| 密度 | 18px 圆角卡片，较多说明性大标题 | 9px 面板、6px 控件圆角、细分割线、紧凑标题与参数 |
| 资源编辑 | 模型和扩展以状态说明为主 | 左侧目录、右侧参数，选择、配置和诊断相连 |
| 运行配置 | 完整 JSON 编辑与确认 | 档案/分区/结构化表单，保留 JSON 检查和严格服务端校验 |
| 追踪 | 运行表格后接独立详情面板 | 数据工作区中的列表与选中详情，服务端过滤分页 |
| 总览 | 个体状态、目标、观测卡片 | 紧凑真实指标、待办、事件与资源入口 |

v4 light tokens：背景 `#f8f9fb`、面板/侧栏 `#ffffff`、文字 `#202636`、次要文字 `#7b8395`、边框 `#e5e8ef`、主色 `#5569cc`；正文 13px、辅助文字 11px、标题 22px，控件 33px，表头 40px，桌面内容边距 30px，移动端 13px，最大内容宽度 1320px。触摸点击区域至少 40×40px，需要与桌面视觉高度分开处理。

包只提供 light 主题。此前用户明确要求的深色主题仍需保留并补齐 v4 深色变量；不能让旧深紫侧栏继续充当浅色 v4。禁止角色形象、人物头像、吉祥物和装饰背景的要求继续适用。

## 3. 借鉴依据与概念边界

已核对包内引用的官方文档：

- [AstrBot WebUI](https://docs.astrbot.app/use/webui.html)明确描述配置档案与分区、插件/Skills/MCP 分组、单插件配置独立，以及统计/对话/日志/追踪工作区。ALIA 采用这些管理流程；具体 230px、配色及 13 页是本包自己的选择。
- [Koishi 安装和配置插件](https://koishi.chat/zh-CN/manual/usage/market)支持市场、配置、依赖分区及安装后单独启用。不能据此声称已经验证所有参考产品当前版本的完整界面和所有细节。

必须做语义适配的地方：

1. 包中用 `subject_id` 指个体根身份，当前工程的根是 `individual_id`；已有 `subject_id` 表示关系/交流对象，不能直接重命名或合并。
2. 原型的实例选择器和“多个个体/配置中复用插件”不能引入种群或多主体管理。当前一个安装实例承载一个活跃个体，运行、模型、渠道及配置选择均不能重置它。
3. 原型中的 Memory Core 插件不表示 ALIA 核心身份、历史存储可随卸载插件消失。内置能力、外部插件、已安装、已启用、已授权和执行成功分别呈现。
4. 原型 WebSocket 地址只是示例。保留当前 REST + SSE，无需因界面样例更换通信架构。
5. 原型里的模型、插件数量、在线状态、默认档案和工具轮数均为 Demo。不得写入生产默认值；既有预算、每循环三次调用及权限校验继续由服务端执行。
6. 收拢认知和关系导航不能删掉领域能力；建议放入身份页的子工作区，保留旧链接兼容。文字交流保留在渠道 Web 子入口，不能因导航合并失去访问路径。

## 4. 仓库现状与可复用基础

现有前端是 React + TypeScript + Vite，使用自有组件和 hash 路由，没有需要替换的第三方 UI 框架。后端是 Rust/Axum/SQLx/PostgreSQL。继续在同一个 WebUI 内重构，保持领域、运行时、适配器和服务边界。

主要复用点：

- `web/src/shared/repository.ts`：真实请求适配、Bearer、幂等键、If-Match、no-store、超时和原文 JSON 提交；不回退为 Demo。
- `useIndividual.ts` / `useResource.ts`：真实状态与 SSE、会话清理、加载错误、卸载后迟到结果处理。访问令牌仅在页面内存。
- `design-system/components.tsx`：原生 dialog、确认反馈、键盘标签导航、空状态等。优先改样式和组合，不复制原型的简化弹窗实现。
- `Settings.tsx`：运行规则的版本冲突处理、确认前对比、失败保留草稿和严格 JSON 路径。结构化编辑应以完整服务端文档作为基线，保留未展示字段，不能拼装缺字段的新配置。
- `Traces.tsx` / `AuditLog.tsx`：已有真实游标分页与选中详情请求，适合重组成工作区。
- `Memory.tsx` / `MemoryPeople.tsx`：记忆类型、来源、人物角色及索引观测；可改为紧凑检索与详情。

现有 `tokens.css` 注释宣称从安装包生成，但实际仍是旧紫白配色与 v3 尺寸。实施时应更新生成/映射说明并让 token 对照可检查，不能凭注释认定已同步。

### 12.4 从原型补全为可实施契约
