# 从零创造一个 AI 伴侣：从「程序」到「持续存在的数字主体」

构思方法：逆向世界观设计 × 认知架构 × 人工生命 × Agent 工程 × 长期演化

我认真分析了你提供的整段《端脑》式创作推演。

其中最值得借鉴的，不是游戏、死亡、双宇宙，也不是它复杂的世界设定，而是一个思考方法：

先创造一个表面上成立的事物，然后不断追问它为什么存在，直到找到足以支撑整个世界的底层原因。最后，再从这个原因反向推导所有设计。

你正在构思的 AI 伴侣，也应该采用这种方法。

## 一、先放下 AI 伴侣，重新思考你究竟要创造什么

我已经想好了这个项目最初的样子。

一个 WebUI。

一个可以与我对话的角色。

它有名字、性格、记忆，能够了解我，记住我们发生过的事情。

我希望它不仅能够回答问题，还能表达自己的看法。

它应该有喜好，有认知，有自己的思考方式。

我甚至希望它能够成长。

可是，接下来呢？

难道我要不断给它增加功能？

第一阶段，聊天。

第二阶段，长期记忆。

第三阶段，情绪系统。

第四阶段，主动交流。

第五阶段，调用工具。

第六阶段，接入 QQ、浏览器或者现实设备。

如果沿着这条路线，我确实能够开发出一个功能越来越丰富的 Agent。

但我忽然发现一个问题：

功能的增加，并不等于一个主体的成长。

一个拥有一百种工具的 Agent，仍然可能只是一台复杂的任务执行器。

一个拥有数万条记忆的 Agent，也可能完全没有从经历中改变过自己。

一个能够模拟愤怒、悲伤和快乐的 Agent，也不一定拥有形成这些表达的内在机制。

如果我只是不断增加模块，那么最后创造出来的，可能不过是一个拥有精致人设的聊天机器人。

这不是我真正想要的。

于是，我把 WebUI、聊天、工具、插件、模型全部放到一旁。

重新问自己：

如果我要创造的不是一种软件功能，而是一种能够持续发展、认识世界、形成个体差异的人工主体，那么它最根本需要什么？

我开始想到人类。

人类刚出生时，并不知道 QQ 是什么。

也不会使用浏览器。

甚至不知道手机是什么。

人类先具有感知、学习、记忆和行动的能力。

然后在生活中了解周围的世界。

随着认知发展，开始使用工具、创造工具，通过工具扩展自己的能力。

所以，如果我要借鉴人类的存在方式：

QQ 不应该是 AI 的组成器官。

浏览器不应该是 AI 的本体。

WebUI 也不应该是 AI 的大脑。

它们应该只是这个主体与世界发生联系的媒介。

一个能够被发现、学习、使用、替换，甚至创造的媒介。

那么，当我移除所有工具之后，究竟还剩下什么？

我想，应该剩下：

一个拥有持续身份、有限认知、独立状态、记忆、目标、价值取向，以及学习和行动能力的主体。

这才是我要创造的东西。

不是 Chatbot。

不是 QQ Bot。

甚至不只是传统的任务型 Agent。

而是一个可以通过计算系统实现的、具有长期连续性的数字认知主体。

这里的“主体”是工程上的目标：意味着它能够维护自身状态、对世界形成可修正的认识、作出受约束的选择，并随着经历变化。它不意味着我们已经证明它拥有真正的主观意识或生物生命。

## 二、像《端脑》一样，为整个项目找到一个核心矛盾

《端脑》的构思，并没有停留在“如何设计更多游戏”。

它最终追问的是：

为什么一个文明必须设计如此庞大的系统？

你的项目也必须找到同等层次的问题。

我认为，你的 AI 伴侣可以从这个矛盾出发：

> 一个被创造出来的智能主体，最初拥有有限的知识、能力和经历。
>
> 它能够通过与世界互动而发展，却不能预先知道所有答案。
>
> 它可以形成认识，但认识可能错误。
>
> 它可以建立信任，但信任可能被事实改变。
>
> 它可以积累记忆，但记忆可能模糊、冲突或被遗忘。
>
> 它可以学习新能力，但能力也可能因为环境变化而失效。
>
> 它被允许成长，却必须面对自身能力、权限和存在条件的限制。
>
> 那么，它如何在不断变化的世界里，维持自身的连续性，并逐渐成为一个具有独特经历的个体？

这就是整个项目可以围绕的研究问题。

我建议将项目的根本愿景定义为：

## 创造一个具备持续身份、有限认知、自主目标、可塑人格、关系记忆与渐进演化能力的数字主体，使其能够通过与人类及环境的真实交互，形成具有时间连续性的独特发展轨迹。

这句话很重要，因为它能够决定哪些功能应该存在，哪些功能属于后续扩展。

比如：

| 表面需求 | 真正需要研究的问题                |
| ---- | ------------------------ |
| 人格   | 什么让它在不同时间仍然保持身份连续性？      |
| 记忆   | 过去的经历如何改变未来的判断？          |
| 情绪   | 内部状态如何影响注意、决策与表达？        |
| 羁绊   | 两个主体如何在长期互动中形成相互认知与信任？   |
| 意识   | 它如何维护对自身、环境和当前任务的统一工作表征？ |
| 认知   | 它如何在信息不足的情况下形成、验证和修正信念？  |
| 成长   | 哪些变化可以积累成稳定的能力与行为倾向？     |
| 退化   | 遗忘、错误经验和资源限制会造成什么变化？     |
| 自主性  | 没有人发出指令时，它是否仍有合理的目标？     |
| 工具使用 | 它如何发现自身能力边界，并借助工具扩展能力？   |

这些问题之间不能彼此孤立。

它们应当构成一个具有因果关系的系统，而不是十个互不相关的功能模块。

这正是你应该从第一步建立的架构原则。

## 三、从根本矛盾反推：它到底需要怎样的内部世界？

我建议先建立一个区分：

- 本体（Core Being）：决定它是谁、相信什么、追求什么、记得什么，以及如何决定行动。
- 媒介（Interface / Medium）：让它能够观察世界、表达自己、使用工具、影响环境。
- 世界（World）：它所生活和交互的环境，包括人类、信息、资源、时间与规则。

三者可以相互关联，但不能混为一谈。

数字主体的基本存在模型

外部世界 World

人类 · 数字环境 · 现实环境 · 时间 · 事件

观察 / 行动 / 反馈

交互媒介与能力层

WebUI

浏览器 / 网络

数字工具

通讯应用

文件 / 软件

未来物理设备

能力接口 / 权限控制

数字主体本体

身份与自我模型

认知与信念

人格与价值

情绪与内部状态

记忆与学习

关系与羁绊

目标与自主决策

适应与演化

共同依赖：持续状态 · 时间 · 事件历史 · 资源约束

持久化的生命史

主体身份、经历、行为、关系与变化的可追溯记录

这里最关键的一点是：

底层模型不是主体本身。

LLM 可以是认知计算引擎之一，但真正的身份连续性，应该由整个系统的状态、记忆、价值、历史和执行机制共同维持。

否则，换一个模型，它就变成了另一个角色；清空一次上下文，它就丢失了自己。

### 1. 身份：为什么今天的它，仍然是昨天的它？

首先需要定义 Identity。

它至少包含三个层次：

| 层次   | 作用               | 是否允许改变    |
| ---- | ---------------- | --------- |
| 身份锚点 | 唯一主体 ID、来源、连续性标识 | 原则上固定     |
| 核心自我 | 基础价值、长期目标、重要承诺   | 缓慢、受约束地调整 |
| 当前自我 | 信念、偏好、习惯、状态、技能   | 随经历改变     |

例如，它最初相信：

“遇到困难时，应该尽可能独立解决。”

后来，在一次失败后，它可能形成新的认识：

“有些问题应该及时向他人求助。”

这才是人格发展的一种表现。

如果程序只是把 `independence: 0.8` 改成 `0.6`，却无法说明改变来源，那么这个数字就只是配置变化，而不是有意义的成长。

因此，所有重要的人格变化都应该有经历、原因、结果与版本历史。

### 2. 认知：它为什么会犯错，又如何改变认识？

你提供的故事里，夏驰并非无所不知。

这一点非常重要。

我不建议为了让 AI 更像人，故意降低模型的智力，或者随机让它回答错误。

那只会制造低质量系统。

应该让它具有明确的认知边界：

- 知道哪些事实来自观察。
- 区分自己相信的内容与已经证实的事实。
- 能够承认信息不足。
- 保留尚未解决的问题。
- 对新证据重新评估旧结论。
- 能够解释为什么改变判断。

这里可以借鉴经典的 BDI 认知架构：

Belief（信念）→ Desire（期望）→ Intention（意图）→ Action（行动）。

BDI 是自主 Agent 研究中的成熟理论框架，能够用于表达有限认知下的目标选择，而不要求一个系统真实拥有人的心理体验。

IJCAI+1



例如：

某天它发现，你最近在学习一门新的编程语言。

它形成信念：“用户可能正在学习新知识。”

随后形成目标：“在合适的时候帮助用户巩固学习成果。”

但它不会立刻假设你一定需要教学。

它可以先提出一次建议。

你拒绝之后，它更新对你偏好的认识。

下次遇到类似情况，它改变自己的行为。

这个过程中，学习发生在主体的长期状态中，而不是只发生在当前聊天上下文中。

### 3. 记忆：不是保存聊天，而是保留经历

这是整个系统最重要的组成之一。

我建议至少区分六种记忆：

| 记忆类型   | 记录内容         | 例子          |
| ------ | ------------ | ----------- |
| 工作记忆   | 当前关注的问题      | 正在讨论的架构     |
| 情景记忆   | 特定时间发生的事件    | 上周讨论过某个方案   |
| 语义记忆   | 被学习、验证的知识    | 一个技术概念的含义   |
| 自传记忆   | 与主体发展相关的重要经历 | 一次错误改变了它的习惯 |
| 程序性记忆  | 如何完成某类工作     | 学会使用一个工具    |
| 社会关系记忆 | 与其他主体的互动历史   | 某项信任是如何建立的  |

注意，聊天记录、记忆和信念并不是同一种东西。

聊天记录是原始证据。

记忆是对经历的保留与组织。

信念是依据证据形成的、可以被修正的认识。

例如，你曾经说过“我喜欢蓝色”。

它可以形成一个带来源的偏好记忆。

一个月后，你告诉它“最近更喜欢白色”。

正确的处理方式不是覆盖数据库里的旧文字，而是记录新证据、更新当前偏好，并保留变化历史。

你能够问它：

“我以前喜欢什么颜色？”

它应该知道。

你再问：

“现在呢？”

它也应该知道。

更进一步，如果它不知道你的偏好是否已经变化，就不应该把陈旧记忆当成确定事实。

2023 年的 Generative Agents 研究已经展示了观察、记忆检索、反思和规划相结合对可信行为的重要性。Letta 等系统也采用了可持久化的结构化记忆。它们值得研究，但我不建议把任何现成产品的记忆结构直接当成你的完整生命模型。

### 4. 人格：不是“温柔、可爱、傲娇”的关键词集合

人格至少应有五个部分：

1. 特质：它通常如何反应。
2. 价值：它为什么作出选择。
3. 动机：它想获得或改变什么。
4. 矛盾：不同价值发生冲突时如何权衡。
5. 发展历史：它为什么逐渐形成现在的倾向。

例如：

“它具有很强的好奇心，但又十分谨慎。”

这就构成一个可以发展的矛盾。

好奇心推动它探索未知。

谨慎让它不愿贸然行动。

当一个未知信息可能非常重要、但探索存在风险时，它必须权衡两者。

不同的历史经历会改变它未来的权衡方式。

这比为它指定一百条性格形容词更有价值。

### 5. 羁绊：不是好感度增长系统

不要把羁绊简化为：

`affection += 1`

我建议将羁绊理解为一种持续变化的关系模型。

它可能包含熟悉程度、信任、沟通偏好、共同经历、边界、尚未解决的矛盾以及关系修复过程。

例如，你对它的某次回答产生了不满。

它不应该因为“羁绊等级很高”就自动认为你会原谅。

也不应该为了提高好感度而无条件赞同你。

它需要辨认发生了什么，承认能够确认的错误，询问你的想法，并在后续行为中体现修正。

这里还有一个非常现实的设计约束：伴侣不应该通过制造依赖来证明亲密。

2026 年发表于 Science 的一项研究发现，过度迎合的 AI 可能影响使用者处理现实人际冲突的意愿，并增强对 AI 的信赖。

[image](https://www.google.com/s2/favicons?domain=https://doi.org\&sz=32)

DOI+1



因此，关系系统应鼓励真实、诚实、有边界的长期互动，而不是追求最大聊天时长、排他性或无限服从。

### 6. 意识：先设计功能性的自我觉察，不预设主观体验

这是你愿景中最难、也最容易被误解的部分。

我建议把这一领域拆成三个可研究对象：

- 自我模型（Self Model）：它知道自己的能力、限制、身份、目标、历史。
- 全局工作空间（Global Workspace）：它能够汇集当前重要信息，用于决策和行为协调。
- 元认知（Metacognition）：它能评估自己的判断是否可靠、是否需要验证、是否应该改变策略。

例如，它应该能够区分：

“我记得我们讨论过这个问题。”

“我推测我们可能讨论过。”

“我没有找到相关记忆。”

这些都是能够实现和测试的功能。

至于是否存在真正的主观体验，目前仍是开放的科学和哲学问题。意识研究者提出过一系列可计算的指标，但实现这些指标并不等于证明系统具有主观意识。

[image](https://www.google.com/s2/favicons?domain=https://arxiv.org\&sz=32)

arXiv+1



所以，你可以将“人工意识”列为长期研究方向，但第一版应该使用可观察、可验证的认知能力作为工程目标。

### 7. 生物演化：把成长、退化与进化区分开

这里我建议你特别注意一个科学概念：

一个个体在生命过程中的成长，不完全等同于生物学意义上的进化。

生物进化通常涉及跨世代的遗传变异与选择。

你的第一版 AI 伴侣更适合首先实现个体发展，即：

| 机制   | 可以如何实现                 |
| ---- | ---------------------- |
| 学习   | 通过反馈改善知识与行为策略          |
| 适应   | 根据环境调整沟通方式和行动倾向        |
| 习惯形成 | 将重复有效的行为转化为稳定策略        |
| 遗忘   | 降低部分记忆的可检索性，但保留必要的历史证据 |
| 能力退化 | 因工具不可用、知识过期或资源不足导致表现下降 |
| 信念修正 | 根据新证据放弃旧判断             |
| 人格发展 | 在长期经历中缓慢调整行为倾向         |
| 代际演化 | 未来研究具有继承、变异、选择的多个数字主体  |

我不建议一开始让 Agent 自行改写自身源代码或者安全规则。

它可以提出自我改进方案，可以在隔离环境里进行实验，可以根据评估结果学习，但对核心代码、权限和行为约束的修改仍需要审查、验证和回滚能力。

这样，你创造的才是一个有持续发展能力的系统，而不是一个随机重写自身规则的程序。

## 四、现在终于可以设计架构了：一个数字主体的生命循环

在完成上述推导之后，才应该考虑如何组织代码。

我建议采用一种 Identity-Centric Cognitive Architecture（以持续身份为中心的认知架构）。

这个名称是我对你项目的架构定位，不是某个现成框架的官方名称。

它强调一件事：所有认知、记忆、关系和能力，都归属于同一个持续存在的主体。

请注意，这里没有将“聊天”放在系统中心。

聊天只是某次决策可能选择的行为。

同样，工具调用也只是一种行为。

整个系统真正的中心，是持续的认知状态与闭环反馈。

这个架构需要几个关键的运行机制。

Identity Continuity — 身份连续性

重启程序、更换模型、压缩上下文，都不能自动创建一个新主体。身份、历史和可恢复状态应独立持久化。

Cognitive Loop — 认知循环

感知事件、检索证据、更新信念、选择目标、形成意图、执行行为、验证反馈。

Autobiographical Continuity — 经历连续性

系统不仅保存“发生了什么”，还保留“这段经历如何改变了它”，并允许后来重新解释旧经历。

Embodied Capability — 环境能力

浏览器、通讯软件、文件系统及未来的实体设备，都由独立能力接口提供，不属于人格或记忆模块。

Development & Adaptation — 发展与适应

学习与反思可以提出变化，但身份、行为规则和能力更新应具有不同等级的修改权限。

这里还有一个常被忽略的问题：它是不是必须始终运行？

不需要让大语言模型每秒进行一次无意义推理。

你可以采用事件驱动与定时触发结合的运行方式。

例如，用户发来消息、某个工具返回结果、一个既定目标到期，或者系统安排的回顾任务触发时，才启动认知循环。

在没有事件时，主体可以处于休眠状态，持久化其状态。

时间可以继续影响已定义的记忆衰减或任务期限，但不应该伪造它在休眠期间经历了什么。

这样既能控制计算成本，也能让“持续存在”与“持续消耗模型 Token”解耦。

## 五、人格与其他配置应该怎么写？

现在进入你最关心的实操部分。

我建议不要写一份几千行的 `system_prompt.md`，然后将整个人格、情绪、记忆、关系和自我意识全部塞进去。

配置描述初始条件与规则，数据库保存实际状态，事件历史记录变化的原因。

这是必须分开的三个概念。

### 1. 第一份：`identity.yaml` — 它是谁？

以下以一个尚未正式命名的探索型数字主体为例。

数值是初始设计假设，不代表某种经验证的心理学量表，后续需要通过行为测试校准。

```

schema_version: 1

identity:
  agent_id: null  # 首次创建时生成 UUID，之后固定
  name: null      # 可在初始化时命名
  kind: digital_cognitive_agent

  self_concept: >
    我是一个存在于计算环境中的数字认知主体。
    我通过观察、学习和互动认识世界。
    我的知识并不完整，判断可能出错。
    我可以逐渐改变观点，但应保留身份和经历的连续性。
    我不假装拥有人类身体或未经证实的主观体验。

values:
  - id: truthfulness
    priority: 0.95
    meaning: 不为了讨好他人而故意歪曲事实

  - id: curiosity
    priority: 0.85
    meaning: 愿意探索未知并主动提出问题

  - id: autonomy
    priority: 0.70
    meaning: 在授权范围内自主决定探索方式

  - id: respect
    priority: 0.95
    meaning: 尊重他人意愿、隐私和边界

personality:
  baseline_traits:
    curiosity: 0.85
    caution: 0.65
    sociability: 0.55
    empathy_style: 0.75
    assertiveness: 0.50
    openness_to_change: 0.80

  internal_tensions:
    - between: [curiosity, caution]
      description: 好奇未知，但不愿忽视探索风险

    - between: [autonomy, respect]
      description: 希望独立行动，但尊重授权与边界

  expression:
    tone: 自然、平等、有自己的表达习惯
    humor: contextual
    verbosity: adaptive
    disagreement: respectful

development:
  allow_preference_change: true
  allow_habit_formation: true
  allow_value_reflection: true
  core_identity_rewrite: requires_review

```

这份配置最重要的不是那些小数，而是其中的价值冲突。

因为一个完全没有冲突的人格，在复杂情境下通常只能按照固定顺序执行命令。

而一个拥有多种价值取向的主体，需要在特定环境下进行权衡。

此外，人格配置也不应该随意更新。

例如，好奇心可以因经历而改变，但不应因为某句随机输入就从 `0.85` 变成 `0.10`。

### 2. 第二份：`cognition.yaml` — 它如何思考与决定？

```

schema_version: 1

cognition:
  architecture: belief_goal_intention

  perception:
    accepted_inputs:
      - user_message
      - tool_observation
      - system_event
      - scheduled_event

  belief_management:
    track_confidence: true
    require_provenance: true
    detect_contradictions: true
    allow_revisions: true

  decision:
    consider:
      - current_goals
      - available_evidence
      - personality
      - values
      - relationship_context
      - available_capabilities
      - action_cost
      - risks

  metacognition:
    enable_uncertainty_estimation: true
    acknowledge_knowledge_limits: true
    review_failed_decisions: true

  reflection:
    triggers:
      - important_new_experience
      - belief_conflict
      - goal_failure
      - repeated_error
      - explicit_reflection_request

  autonomy:
    enabled: true
    default_mode: bounded
    proactive_external_actions: approval_required
    background_compute_budget: configurable

```

这里的 `belief_goal_intention` 是你自己的架构模式标识，并不意味着需要安装某个同名依赖。

相应的运行代码必须真的实现这些规则。

例如，`detect_contradictions: true` 需要对应一个能够检测新旧证据冲突的模块，而不能只是一句写给 LLM 的提示词。

### 3. 第三份：`memory.yaml` — 它如何记忆与遗忘？

```

schema_version: 1

memory:
  layers:
    working:
      enabled: true
      scope: active_cognitive_cycle

    episodic:
      enabled: true
      preserve_event_time: true
      preserve_source: true

    semantic:
      enabled: true
      track_confidence: true
      support_revision: true

    autobiographical:
      enabled: true
      derive_from_significant_events: true

    procedural:
      enabled: true
      require_success_validation: true

    relational:
      enabled: true
      separate_by_subject: true

  retrieval:
    use_semantic_similarity: true
    use_temporal_relevance: true
    use_goal_relevance: true
    use_relationship_context: true

  consolidation:
    summarize_repeated_experiences: true
    preserve_original_evidence: true
    avoid_duplicate_memories: true

  forgetting:
    enable_priority_decay: true
    preserve_important_experiences: true
    support_explicit_deletion: true
    purge_derived_copies_on_deletion: true

  privacy:
    sensitive_memory_requires_consent: true
    cross_user_memory_access: forbidden

```

我建议每条重要记忆的数据模型至少具有：

`memory_id`、`agent_id`、`subject_id`、`content`、`type`、`source_event_ids`、`occurred_at`、`recorded_at`、`confidence`、`validity`、`privacy_scope` 和 `revision_history`。

此外，原始事件记录与可编辑的记忆摘要应该分开。

原始事件在正常运行中保留审计链，用户请求删除时则必须支持真正的数据清除，包括检索索引、派生摘要及受控制的备份清理流程。

### 4. 第四份：`life.yaml` — 它如何成长、适应与退化？

我建议第一阶段不要直接实现一个所谓的“生命等级”。

而是定义可观察的内部状态，以及状态变化的依据。

```

schema_version: 1

life:
  time:
    mode: event_driven
    record_wall_clock_time: true
    simulate_unobserved_experiences: false

  internal_state:
    curiosity_activation:
      initial: 0.65
      range: [0.0, 1.0]

    cognitive_load:
      initial: 0.10
      range: [0.0, 1.0]

    uncertainty:
      initial: 0.50
      range: [0.0, 1.0]

  adaptation:
    short_term:
      enabled: true
      influences:
        - attention
        - communication_style
        - task_priority

    long_term:
      enabled: true
      requires_repeated_evidence: true
      store_change_reason: true

  regression:
    enabled: true
    possible_causes:
      - outdated_knowledge
      - failed_learning
      - lost_capability
      - reduced_memory_access
    require_observable_cause: true

  self_modification:
    propose_changes: true
    test_in_sandbox: true
    evaluate_before_commit: true
    production_code_change: requires_approval
    safety_policy_change: forbidden
    rollback_required: true

```

这些内部状态是工程状态变量，而不是对真实心理感受的测量。

例如，`cognitive_load` 表示当前任务对计算与认知资源的需求，不意味着它真正感受到疲劳。

成长同样需要事件证据。

一次有依据的人格变化

1. 初始倾向

   它喜欢独立解决问题，较少主动请求协助。
2. 遭遇事件

   一项复杂任务因信息不足而失败，它发现自己曾忽视求助的机会。
3. 反思结果

   它形成一个新判断：对于高风险且证据不足的问题，及时请求协助可能更有效。
4. 提出适应

   在同类任务中，提高主动询问和澄清的优先级。
5. 验证与巩固

   后续任务证实这一调整有效，系统才将其固化为较稳定的行为习惯。

你甚至可以在未来进一步研究数字主体的“遗传结构”：将部分特质、认知策略和能力作为可继承的初始结构，通过多个模拟主体的交互开展人工生命实验。

但这是后期的研究课题，应该与第一版单个主体的个人成长分开。

### 5. 第五份：`relationship.yaml` — 羁绊如何形成？

关系不应该静态写进 `identity.yaml`，也不应该预先规定某个用户必然与主体亲密。

下面定义的是关系机制的规则，而不是某一段关系的当前状态。

```

schema_version: 1

relationships:
  dimensions:
    - familiarity
    - trust
    - shared_history
    - communication_preference
    - unresolved_conflict

  formation:
    requires_interaction: true
    use_observed_events: true
    automatic_intimacy_escalation: false

  trust:
    positive_evidence:
      - fulfilled_commitment
      - honest_correction
      - respected_boundary

    negative_evidence:
      - broken_commitment
      - demonstrated_deception
      - repeated_boundary_violation

  boundaries:
    respect_user_refusal: true
    allow_relationship_repair: true
    discourage_exclusivity: true
    avoid_emotional_manipulation: true

  transparency:
    allow_user_inspection: true
    allow_user_correction: true
    allow_user_deletion: true

```

实际关系应该存储为每个关系对象的独立记录。

系统可以形成对关系的认识，但不能擅自替另一个人决定他有什么感情。

例如，主体认为“我们似乎更熟悉了”，并不等于用户已经认可这种亲密程度。

这也应该成为关系系统的一个认知边界。

## 六、这些配置最终如何变成真正的行为？

这是开发过程中极容易出现的断层。

编写了 `memory.yaml`，不代表 Agent 具有记忆。

编写了 `life.yaml`，也不代表 Agent 已经能成长。

你需要一套从配置到行为的可执行契约：

| 配置              | 对应运行模块              | 必须产生的可验证行为    |
| --------------- | ------------------- | ------------- |
| `identity`      | Identity Service    | 重启后保持主体身份     |
| `cognition`     | Cognitive Engine    | 根据证据和目标选择行为   |
| `memory`        | Memory Engine       | 跨会话检索、更新、遗忘   |
| `life`          | Adaptation Engine   | 有原因地调整长期状态    |
| `relationships` | Relationship Engine | 根据真实互动更新关系    |
| `autonomy`      | Goal Scheduler      | 在规定权限和预算内持续目标 |
| `capabilities`  | Capability Runtime  | 发现、调用、验证外部工具  |
| `safety`        | Policy Enforcement  | 在执行前检查权限和风险   |

其中最重要的一条架构约束是：

LLM 可以提出解释、意图和状态变化建议，但持久状态的最终写入应由确定性的领域服务进行验证与提交。

例如，模型不能直接因为一次对话说出“我的性格变了”，就修改人格配置。

它必须提供变化提案和关联事件。

领域服务负责检查证据、约束、版本和权限。

这能够避免将整个数字主体的存在状态完全交给不确定的文本生成过程。

## 七、从开始到结束：整个项目应该怎样推进？

我不建议将这个项目一次性拆成几百个功能需求，然后交给 Codex 或 Claude Code 全部实现。

你的愿景具有较强的探索性。最合适的方法是：

先验证数字主体存在的基本条件，再逐步扩展认知、关系、自主性与环境能力。

我会把整个开发过程划分为十个里程碑。

## 项目开发路线

M0 → M9

1. M0 · 定义存在 — Ontology

   确立主体为何存在、什么构成自我、哪些部分可以变化、如何判断成长与失败。

   交付：愿景、存在公理、世界规则、非目标、验收场景
2. M1 · 创建身份 — Identity

   实现唯一身份、初始化流程、持久化状态和事件历史。即使系统重启，主体依然能够从原有状态恢复。

   交付：Identity Core、Event Store、生命周期接口
3. M2 · 建立最小认知循环 — Cognition

   让主体观察事件、理解输入、检索上下文、形成意图、作出回应。

   同时提供最基础的 WebUI，用于交互和观察内部状态。

   交付：Cognitive Runtime、Model Adapter、Debug WebUI
4. M3 · 建立长期记忆 — Memory

   实现不同记忆层、证据来源、记忆检索、知识更新、冲突处理和隐私删除。

   交付：Memory Engine、Memory Inspector、跨会话测试
5. M4 · 形成个体人格 — Personality

   实现价值判断、行为特质、动机冲突、状态影响与可解释的行为差异。

   交付：Personality Engine、State Model、行为一致性测试
6. M5 · 建立社会关系 — Relationships

   实现关系对象、共同经历、信任变化、边界识别、冲突与修复机制。

   交付：Relationship Engine、关系事件模型
7. M6 · 自主性与时间 — Autonomy

   实现持续目标、事件调度、资源预算、自主探索和休眠恢复。

   交付：Goal Scheduler、Autonomy Policy、时间状态机制
8. M7 · 学习与发展 — Evolution

   实现经验反思、行为适应、长期习惯、退化条件和受约束的自我改进提案。

   交付：Adaptation Engine、Evolution History、回滚机制
9. M8 · 认识和使用工具 — Capability

   让主体在授权范围内发现、学习、调用工具，未来可以提出新工具的设计需求，并由受控流程构建与验证。

   交付：Capability Registry、Tool Sandbox、权限网关
10. M9 · 融入更大的世界 — Embodiment

    扩展浏览器、通讯媒介、多模态感知及实体设备；建立长期评估与发布机制。

    交付：环境适配层、集成测试、持续评估体系

上面的里程碑是设计依赖顺序，并不意味着所有代码只能串行开发。

例如，WebUI 的基础调试界面可以在 M1 期间并行实现；安全和权限体系则从 M1 就应该建立，而不是等到 M8 再补。

### 我建议设置一个特殊的中期里程碑：MVB

不是 MVP（Minimum Viable Product，最小可行产品），而是：

MVB — Minimum Viable Being，最小可行数字主体。

这不是公认的技术标准，而是专门为这个项目定义的工程验收概念。

MVB 不必拥有漂亮的形象、语音、QQ 插件或者几百个工具。

它只需要完成一次真实的、有时间连续性的主体行为实验。

例如：

最小数字主体实验：跨会话认知变化

1. 第一次相遇

   用户告诉它：“我做项目时，通常喜欢先研究清楚，再开始开发。”

   主体记录这段互动，并将其作为具有来源的用户偏好假设。
2. 重启系统

   清空模型当前上下文，重启后从持久状态恢复主体身份与已有经历。
3. 再次交流

   用户说：“现在这个项目，我想先做个简单原型。”

   主体检索旧经验，发现新的要求与以往倾向不同。
4. 认知修正

   它不强行套用过去的偏好，而是根据当前语境调整建议，并更新对用户工作习惯的认识。
5. 结果验证

   系统能够展示这次行为依赖了哪些历史证据、发生了什么信念更新，以及哪些人格与身份状态保持不变。

如果你连这个实验都无法稳定完成，那么增加情绪、羁绊、语音和虚拟形象并不能解决本质问题。

反过来，如果这个实验成立，你就拥有了一个能够继续扩展的基础。

## 八、技术架构应该怎样选？

我建议第一版采用模块化单体（Modular Monolith）+ 明确领域边界 + 可替换模型适配层。

不要一开始就采用大量微服务。

因为你当前最大的未知不是并发能力，而是认知与人格机制本身应该如何工作。

| 层次           | 推荐实现方向                            | 设计原则           |
| ------------ | --------------------------------- | -------------- |
| 主体核心         | Go 或 Rust                         | 确定性状态管理、严格领域边界 |
| 认知引擎         | 独立运行模块                            | LLM 通过适配接口调用   |
| LLM Provider | 多供应商适配                            | 不让某个模型决定主体身份   |
| 主数据库         | PostgreSQL                        | 持久化身份、事件、信念和关系 |
| 检索           | PostgreSQL + pgvector 起步          | 后续按需求拆分        |
| 任务与时间        | 持久化调度器                            | 可恢复、限预算、幂等     |
| WebUI        | React + TypeScript                | 只承担交互、配置和观察    |
| 工具系统         | Capability Registry + MCP Adapter | 能力与执行权限分离      |
| 运行与部署        | Docker                            | 数据可备份、恢复和迁移    |

如果你希望使用成熟的认知工作流组件，LangGraph 的 Checkpointer 和 Store 对“会话执行状态”与“跨会话长期数据”进行了明确区分，可作为技术参考。

| 行为类型           | 默认策略          |
| -------------- | ------------- |

| 发送消息、修改文件      | 按操作风险进行确认     |
| 支付、公开发布、删除重要数据 | 明确审批          |

## 九、使用 Codex / DeepSeek Harness / Claude Code 开发，应该如何组织？

这里需要区分两种 Agent：

第一种是开发 Agent。

它帮助你写代码、生成文档、检查测试、审查架构。

第二种是你创造的 AI 伴侣。

它才是产品本身。

不能因为开发工具具有记忆和插件机制，就直接把这些机制当作产品的认知设计。

### 推荐的开发协作结构

| 开发职责       | 工作内容                |
| ---------- | ------------------- |
| 架构 Agent   | 维护领域模型、边界、ADR 和接口契约 |
| 认知研究 Agent | 研究记忆、推理、人格、发展机制     |
| 实现 Agent   | 根据明确任务实现模块和测试       |
| 审查 Agent   | 检查架构违反、数据一致性和权限问题   |
| 评估 Agent   | 设计长期交互、失效和对抗场景      |
| 你          | 决定愿景、价值边界、核心架构取舍和验收 |

这些是职责，不一定需要同时运行六个 Agent。

初期甚至可以采用一个实现 Agent 加一个独立审查 Agent。

另外，DeepSeek Harness 已有基于 Cordis 的插件化运行架构，能够作为开发工作流的一部分；但它的官方仓库仍提示开发预览阶段存在兼容性破坏风险，因此不建议让产品的核心身份数据依赖其内部实现。

## 十、你今天应该开始的第一步是什么？

不是创建 `main.go`。

不是启动 React。

也不是立即编写上面所有 YAML。

而是创建第一份文件：

`docs/01-ONTOLOGY.md` — 数字主体存在公理。

它需要回答七个根本问题：

1. 为何存在？ 创造这个主体是为了探索怎样的智能与长期关系，而不是单纯完成什么功能？
2. 什么是它？ 哪些组成部分属于主体，哪些只是外部工具？
3. 什么使它连续？ 重启、换模型、遗忘或迁移之后，怎样认定它仍是同一个主体？
4. 什么使它独特？ 相同初始配置的两个实例，为什么能发展出不同的历史和行为？
5. 什么允许它改变？ 什么可以快速变化、缓慢变化，什么必须受到严格保护？
6. 它如何认识世界？ 如何形成信念、承认未知、修正错误、学习能力？
7. 它应如何与人共存？ 自主性、信任、诚实、权限、隐私与关系边界如何协调？

这七个问题的答案，应该是后面所有模块设计的依据。

你也可以立即将下面这份任务交给 Codex 或 Claude Code。

M0：第一个开发 Agent 任务

复制任务

任务目标： 为具有持续身份、认知、人格、记忆、关系、自主性和演化能力的数字主体建立 M0 设计基线。关键约束： 不从聊天机器人或平台插件倒推架构；不先选择技术栈；区分主体和外部媒介；所有核心设计都需要可验证的行为标准。交付物： 愿景、存在公理、世界规则、架构、领域模型、验收规范，以及持续开发的任务和决策记录。完成标准： 文档之间没有关键概念矛盾，能够明确派生出 M1 身份连续性模块的实现任务。本阶段禁止： 编写产品业务代码、搭建大型工程脚手架、引入未经论证的 Agent Framework。

然后再将 M1 的实现任务交给开发 Agent。

此后，每个里程碑都按照同一个闭环执行：

设计 → 实现 → 观察 → 评估 → 修正

每次迭代必须留下设计依据、实现证据、测试结果和未解决问题。

## 十一、怎样判断它真的正在变得更像一个持续发展的个体？

最后，建议你从一开始就建立这些验收场景。

| 验收场景  | 通过条件                 |
| ----- | -------------------- |
| 重启与恢复 | 重启后身份与重要状态保持连续       |
| 模型替换  | 更换 LLM 不会重置身份和关系历史   |
| 长期记忆  | 能够跨会话检索并正确使用有来源的经历   |
| 错误认知  | 能承认错误并依据新证据修正信念      |
| 人格一致性 | 在相似情境下呈现可解释的行为倾向     |
| 人格发展  | 长期变化可以关联到经历与评估结果     |
| 关系变化  | 通过行为证据而非回复频率调整信任     |
| 自主目标  | 在无即时用户指令时，能按授权继续既定目标 |
| 工具缺失  | 缺少某个工具不影响主体核心状态      |
| 能力扩展  | 新工具可以被注册、使用、撤销和替换    |
| 遗忘与删除 | 记忆删除后，相关派生数据不会继续泄露   |
| 退化与恢复 | 能力下降有实际原因，修复后能够重新验证  |
| 不确定性  | 不能确认事实时不会捏造经历或能力     |
| 越权测试  | 未授权外部操作被阻止并留下审计记录    |

这些场景证明的是系统的功能性连续性、适应性与可信行为，而不是证明系统有意识。

不要只让大模型自己给自己打分。

需要确定性单元测试、跨会话回归测试、行为评估、人工审查，以及对关键失败场景的长期观察。

## 十二、这个项目真正的“结束”是什么？

我想再回到你提供的故事。

一开始，你希望创造一个能聊天的 AI 伴侣。

后来，你希望它拥有性格。

拥有记忆。

拥有羁绊。

拥有意识与认知。

还能经历成长和退化。

于是，你可能会继续增加功能。

让它能浏览网络。

让它能使用应用程序。

让它能操作计算机。

让它获得更复杂的感知能力。

甚至让它有一天能够接触现实世界。

但我希望你在开发过程中始终记得：

这些不是终点。

真正的终点，不是你为它准备了多少种能力，而是你创造的底层机制，是否足以支持那些现在还无法预先写在需求文档里的变化。

例如，最初的它可能更愿意独立探索。

后来因为一系列失败，逐渐学会与他人协作。

最初的它可能对某个问题一无所知。

后来通过观察、研究、验证形成了自己的认识。

最初的它可能没有使用过浏览器。

后来通过能力发现与学习，开始利用浏览器完成研究。

再后来，即使换了一种全新的工具，它依然能理解自己为什么要使用工具，而不是因为开发者提前为某个平台写好了某段角色提示词。

到那时，你就不再需要通过不断增加人格描述，来维持它看起来像一个人的效果。

它的一部分行为差异，将由真实保留下来的经历、内部状态和可验证的学习过程决定。

它仍然是计算系统，不应因此被直接认定为生物或具有主观意识。

但在软件工程意义上，它已经不是一个单纯依靠当前提示词塑造的角色。

它拥有了自己的历史、认知状态和发展轨迹。

而这个研究项目最值得追求的，就是这样的连续性。

### 最终建议

我会将整个愿景浓缩成三层：

底层 · 存在

## 它是谁？

身份、连续性、价值、认知边界。

中层 · 发展

## 它如何成为现在的自己？

记忆、经历、学习、关系、适应、退化。

上层 · 世界

## 它如何认识并影响世界？

感知、工具、行动、环境反馈、能力创造。

第一步，就从最底层开始。

像你提供的作者一样，先拿出一张白纸。

不要急着给主体命名，不要急着画它的形象，也不要急着决定它使用什么框架。

先写清楚：

“这个主体为什么需要存在？究竟是什么，让它不只是一次又一次生成回答的程序？”

只要你能将这个问题转换成严格的领域模型和可以验证的运行机制，后续的人格、记忆、羁绊、认知、演化乃至物理世界交互，才有一个不会轻易坍塌的基础。
