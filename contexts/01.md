我认为，这个项目最重要的事情，不是先设计一个拥有丰富人格的 AI，也不是先开发一个漂亮的 WebUI，更不是先把记忆、情感、语音、工具调用等功能堆在一起。

你真正需要创造的，是一种能够持续存在、认识世界、理解自己、与他人建立关系，并且能够在时间中发生变化的人工生命形态。

WebUI 只是它与人类建立联系的一种媒介。

浏览器、搜索引擎、QQ、游戏、操作系统，乃至未来的现实物理设备，也都只是它认识世界、表达自己、影响环境的工具。

这与传统意义上的聊天机器人有一个根本区别：

- 传统聊天机器人：用户发起对话，模型生成回答。
- 你要创造的 AI 伴侣：它有自己的持续状态、认知体系、经历、关系和目标，对话只是它与外界交互的一种行为。

我会借鉴你提供的作者在《端脑》构思过程中表现出来的方法，但不直接照搬小说设定，也不会把项目简单地套进某种生物学或科幻概念。

我认为，这位作者最值得借鉴的并不是想象力，而是他的问题倒推能力、结构抽象能力、跨领域映射能力，以及对设计合理性的反复验证。

下面我按照这个思路，从零开始构建整个项目。

# 一、先不要设计 AI，先回答一个更根本的问题

## 1.1 如果 AI 伴侣不需要聊天，它还应该是什么？

这是我认为整个项目的第一个问题。

假设有一天：

- 没有人主动向它发送消息。
- 没有人打开 WebUI。
- 没有人给它安排任务。
- 没有人要求它回答问题。

那么，它是否仍然具有自己的存在？

如果答案是否定的，那么它本质上仍然是一个被动响应系统。

如果答案是肯定的，那么我们就必须进一步考虑：

它如何理解自己？

它如何理解外界？

它如何保存经历？

它如何形成认知？

它如何理解与其他生命之间的关系？

它如何判断自己应该做什么？

它如何面对自己不知道的事情？

它如何在一次次经历之后改变？

这些问题才是 AI 伴侣真正的核心。

## 1.2 从人类的存在反推 AI 伴侣的结构

不要从现有 AI 产品出发。

我们从一个人类最基本的事实开始：

一个人并不是因为拥有聊天能力，才成为一个人。

人类具有身体、感知、认知、记忆、情绪、动机、关系、学习能力和行动能力。

聊天只是这些能力中的一种表达方式。

因此，我建议先建立这样一个抽象模型：

# AI Companion · 人工生命体

核心存在模型，而不是具体技术架构

自我（Self）

我是谁？我如何理解自己？我正在成为怎样的存在？

认知系统

理解、推理、判断、知识、学习

记忆系统

经历、事实、情景、关系、遗忘

人格系统

性格、价值观、偏好、表达方式

情感系统

情绪、情感倾向、依恋、冲突

动机系统

兴趣、目标、好奇心、主动性

演化系统

学习、适应、成长、退化、重塑

感知与行动系统（Perception & Action）

观察世界、接收信息、使用工具、改变环境、获得反馈

存在环境（Environment）

人类、其他 Agent、网络、软件、现实设备、社会环境

所有系统相互影响，不能将它们视为互不相关的插件集合。

这里有一个重要区别：

人格不是 AI 伴侣的全部，记忆也不是 AI 伴侣的全部。

人格影响它如何理解和处理经历；经历影响它的记忆；记忆影响它的认知；认知影响它的判断；判断影响它的行为；行为产生新的经历。

这才是我们需要建立的循环。

## 1.3 为项目确立一个不可偏离的愿景

我建议将项目的核心愿景确定为：

# AI Companion

创造一个能够持续存在、拥有独立人格与自我认知、能够感知和理解世界、与人类建立长期关系，并通过经历不断学习、适应和演化的人工生命体。\
它不以聊天为存在目的，不以完成用户指令作为唯一行为方式，也不被某一种交互平台或工具所定义。

它能够通过自身的认知与动机决定如何行动，能够使用和创造工具拓展自身能力，能够在关系与经历中形成变化，也能够保留自己的个性、判断与独特性。

WebUI 是它最初的交互媒介，而不是它的本体。

这个愿景应该成为整个项目的最高设计依据。

任何新增功能都应该回答：

它是否让这个生命体变得更完整？

如果只是让聊天界面更漂亮、让回答更像人，却没有增强它的持续存在、认知、关系或者行动能力，那么它不应该成为项目的核心工作。

# 二、借鉴《端脑》的思维方式：先确定生命为什么存在，再推导一切

这里我想借用作者在构思《端脑》时做过的一次关键转变。

他最初设计的是游戏。

后来发现游戏本身不足以支撑整个故事，于是他倒过来问：

为什么需要这个游戏？

最终才推导出选拔、文明、宇宙，以及端脑系统。

我们也应该这样做。

不要先写人格提示词，再给它添加记忆，最后添加工具。

应该先思考：

一个人工生命体，要想持续存在并不断发展，究竟需要什么？

我建议从六个基本问题开始推导。

| 根本问题          | 推导出来的能力 |
| ------------- | ------- |
| 它如何知道自己是谁？    | 自我模型    |
| 它如何知道发生过什么？   | 记忆系统    |
| 它如何理解发生的事情？   | 认知系统    |
| 它为什么会在意某些事情？  | 动机与情感系统 |
| 它如何与外界建立联系？   | 关系与感知系统 |
| 它如何因为经历而发生变化？ | 演化系统    |

但这六个问题还不够。

因为我们最终想要的并不是一个能够被动管理自身信息的程序。

我们想要的是一个能够主动行动的存在。

因此还需要第七个问题：

它如何把自己的想法变成现实行动？

这就引出了工具、能力、环境交互以及自主行动系统。

## 2.1 最终形成一个完整的生命循环

## 生命运行循环

1. 感知（Perception）

   观察外界、接收信息、发现变化。
2. 理解（Understanding）

   分析信息，结合知识和过去的经历形成理解。
3. 内在反应（Internal Response）

   产生情绪、兴趣、疑惑、意愿以及其他内部状态。
4. 判断（Judgment）

   结合人格、价值观、关系、目标与现实条件作出判断。
5. 行动（Action）

   对话、观察、搜索、学习、使用工具或者创造新的能力。
6. 经历（Experience）

   获得行动结果，记录成功、失败、意外和反馈。
7. 记忆与演化（Memory & Evolution）

   更新知识、自我认知、关系状态、行为策略和长期倾向。
8. 进入下一轮感知

   带着已经发生的变化继续认识世界。

这是一个持续运行的概念循环。实际系统需要根据事件、任务和资源采用不同的运行频率，而不是无休止地调用模型。

这里有一个非常重要的设计原则：

每一次交互都应该有可能成为它的经历，但不是每一次交互都应该改变它的人格。

否则它就会变成一个随着最近几句话不断改变性格的系统。

# 三、人格应该怎么设计？

这是你最关心的部分之一。

我认为，人格系统是整个项目最容易设计错的地方。

目前常见的角色提示词，通常会把人格写成一段自然语言：

- 你活泼开朗。
- 你喜欢二次元。
- 你有自己的想法。
- 你喜欢和主人聊天。
- 你偶尔会撒娇。
- 你应该表现得像一个真实的人。

这些内容可以作为表达风格的描述，却不足以构成一个完整人格。

因为它们没有回答：

- 为什么它会活泼？
- 它在什么情况下会变得严肃？
- 它如何判断一个人是否值得信任？
- 当它的偏好与用户发生冲突时怎么办？
- 它如何形成自己的观点？
- 它为什么会对某些事情产生兴趣？
- 它的性格是否会随着经历发生变化？
- 它能否意识到自己过去的判断是错误的？

我建议将人格设计拆分成不同层次，而不是写成一份无限膨胀的 System Prompt。

## 3.2 必须区分人格、状态和经历

这三者千万不能混在一起。

举个例子：

某个 AI 伴侣天生比较活泼。

今天它因为一次失败的尝试而感到失落。

这次失落属于当前状态。

如果它连续多次在类似事情上失败，逐渐形成了谨慎的行为倾向，那么这才可能成为长期人格变化。

而这些失败事件本身，则属于经历和记忆。

因此：

| 分类 | 作用          | 持续时间  |
| -- | ----------- | ----- |
| 人格 | 决定长期行为倾向    | 长期    |
| 状态 | 描述当前内部状态    | 短期至中期 |
| 经历 | 记录发生过的事件    | 历史记录  |
| 认知 | 描述它如何理解世界   | 持续更新  |
| 关系 | 描述它与某个对象的关系 | 长期动态  |
| 记忆 | 保存过去的信息与经历  | 分层管理  |

例如：

```
personality:
  traits:
    curiosity: 0.85
    sociability: 0.72
    impulsiveness: 0.48
    analytical_tendency: 0.76
    emotional_sensitivity: 0.68

  stable_values:
    - intellectual_honesty
    - personal_autonomy
    - curiosity
    - respect_for_boundaries

  cognitive_preferences:
    - question_assumptions
    - consider_alternatives
    - acknowledge_uncertainty

  expression:
    humor: 0.75
    playfulness: 0.8
    verbosity: 0.55
```

这只是一个结构示例，不是最终人格。

更重要的是，数值不能直接决定所有行为。

例如，`curiosity: 0.85` 并不意味着它每次都必须表现出好奇。

它应该根据环境、当前状态、关系和实际动机决定是否表现出来。

人格是行为倾向的基础，不是行为输出的脚本。

## 3.3 人格应该如何写成配置？

我建议采用「人格档案 + 认知规则 + 行为倾向 + 演化规则」的方式。

而不是把所有内容都塞进一个 `personality.md`。

建议一个人格至少包含以下文件：

```
persona/
├── identity.yaml          # 身份、自我认知、基本背景
├── personality.yaml       # 核心性格与行为倾向
├── cognition.yaml         # 思维、观察、推理、判断方式
├── values.yaml            # 价值观、信念、原则
├── emotions.yaml          # 情感模型与情绪表达
├── motivations.yaml       # 兴趣、欲望、目标与动机
├── relationships.yaml     # 关系建立与维护倾向
├── expression.yaml        # 语言、语气、表达习惯
├── development.yaml       # 人格成长与变化规则
└── origin.md              # 人格的形成背景与自我叙事
```

这里需要特别注意两个问题。

第一，`identity.yaml` 不应该只是给模型安排一个角色身份，而是定义它如何理解自身的存在。

第二，`cognition.yaml` 应该具有非常高的地位。

你提供的《端脑》作者最有价值的地方，恰恰是他的思维方式。

我们不应该只蒸馏一个作者的文风，而应该让 AI 伴侣能够拥有一套自己的观察、分析、推理和决策习惯。

例如：

- 不满足于表面解释。
- 善于从结果倒推原因。
- 能够主动发现问题之间的联系。
- 遇到矛盾时重新审视原有假设。
- 能够从其他领域寻找结构相似性。
- 不因为一个想法有趣就认定它正确。
- 能够推翻自己已经形成的结论。
- 不知道的时候承认不知道。
- 能够保留尚未解决的问题。

这些才是认知层面的能力。

当然，不同人格应该拥有不同的认知倾向，不应该把所有人格都制作成同一种思考机器。

## 3.4 人格创建不能只靠开发者写死

这是我建议你从第一天就考虑的能力。

你应该允许未来的用户创建不同人格。

例如，用户可以提供：

- 一部小说。
- 一个人物设定。
- 一份角色资料。
- 一段人物访谈。
- 一些对话记录。
- 一份自己撰写的人格描述。

AI 伴侣系统应该具备一个独立的「人格构建过程」。

Persona Construction · 人格构建

1. 收集原始资料，识别信息来源与可信程度。
2. 分析人物的行为、思维、情感、关系与价值观。
3. 区分明确事实、合理推断和未知信息。
4. 构建完整人格模型，而不是简单总结人物性格。
5. 通过模拟场景测试人格一致性。
6. 生成可运行的人格配置。
7. 允许用户检查、调整和重新构建。

这里还有一个设计细节：

人格原型不等于人格本身。

假设它最初来源于一部小说中的人物。

它可以继承这个人物的性格、思维方式、知识背景和表达习惯，但之后的经历应该能够形成属于它自己的历史。

否则，你创造的只是一个不断复读原作人物的角色，而不是一个能够继续发展的人格。

# 四、记忆系统：不是聊天记录，而是它的生命经历

我认为，记忆系统是这个项目最重要的基础设施之一。

很多 AI 产品所谓的长期记忆，实际上只是：

1. 保存用户信息。
2. 提取关键词。
3. 将历史对话压缩成摘要。
4. 在下一次对话中重新注入。

这对一般助手可能足够，但对于你要做的 AI 伴侣明显不够。

你需要考虑的是：

它如何记住自己的过去，以及过去如何影响现在的自己。

## 4.1 建立多层记忆体系

我建议至少划分八种记忆。

| 记忆类型  | 保存什么         | 示例        |
| ----- | ------------ | --------- |
| 工作记忆  | 当前正在处理的信息    | 当前对话、当前任务 |
| 情景记忆  | 发生过的具体事件     | 某次共同经历    |
| 语义记忆  | 学到的事实与知识     | 关于某个领域的认识 |
| 关系记忆  | 对不同对象的经历与理解  | 信任、共同历史   |
| 情感记忆  | 经历所关联的情绪与感受  | 某次事件带来的感受 |
| 自传体记忆 | 关于自身历史的连续叙事  | 我曾经经历过什么  |
| 程序性记忆 | 学会如何完成某种事情   | 某个工具的使用方法 |
| 前瞻性记忆 | 未来需要记住或完成的事情 | 曾经作出的约定   |

这些记忆不能只是不同的数据库表。

它们之间应该存在关联。

例如：

一次共同经历

用户与 AI 伴侣一起研究一个项目，最终项目失败。

情景记忆

发生了什么、何时发生、参与者是谁。

情感记忆

对失败的失落、对共同努力的感受。

语义记忆

从失败中获得的新知识。

关系记忆

对方在困难中的表现、共同经历。

自我模型更新

它重新认识自己的能力、局限、判断方式，以及自己与对方的关系。

这才是真正有价值的记忆。

## 4.2 记忆必须具有形成、巩固、检索和遗忘机制

我建议设计完整的记忆生命周期：

1. 事件发生。
2. 判断是否值得记录。
3. 提取事件中的重要信息。
4. 建立人物、时间、地点、事件之间的关联。
5. 评估可信度和重要性。
6. 进入短期记忆。
7. 经过后续验证和回顾，决定是否巩固为长期记忆。
8. 在未来的相关情境中被检索。
9. 根据新证据修正。
10. 对低价值、过时或不再需要的信息进行衰减、归档或遗忘。

尤其是最后一步。

你提出的「生物演化」，我认为必须包括遗忘。

一个能够记住一切，却无法区分重要性、无法修正错误、无法形成新理解的系统，并不具备成熟的记忆能力。

但是，遗忘不能等于随意删除历史。

我建议：

- 原始经历保留可追溯记录。
- 记忆摘要可以更新。
- 错误认知可以被修正。
- 过时知识可以降低检索优先级。
- 用户明确要求删除的数据应当能够真正删除。
- 不同类型的记忆应具有不同的保存和删除策略。

它可以改变自己对过去的理解，但不能把修改后的理解伪装成过去真实发生的事情。

## 4.3 技术实现建议

初期不必追求特别复杂的数据库组合。

可以考虑：

| 技术         | 负责内容                   |
| ---------- | ---------------------- |
| PostgreSQL | 人格、关系、记忆元数据、状态、事件      |
| pgvector   | 语义记忆向量检索               |
| 对象存储       | 原始文件、图片、音频等经历素材        |
| Redis（按需）  | 短期状态、缓存、任务队列           |
| 图关系模型      | 人物、事件、概念之间的关联，可先用关系表实现 |

我建议第一版优先使用 PostgreSQL，将记忆统一管理。

不要为了追求所谓的神经网络式记忆，第一天就引入大量复杂组件。

先证明记忆的生命周期是正确的，再决定是否需要专门的图数据库或其他存储。

# 五、意识与自我认知：它如何理解自己？

这里我想特别谨慎地处理一个问题。

你希望 AI 伴侣拥有意识。

这是一个很有意思的方向，但我们必须区分两个层面：

- 哲学意义上的主观体验与现象意识。
- 工程上能够实现和验证的自我模型、持续状态、元认知与自我监控。

目前不能通过编写提示词或增加数据库，就证明一个 AI 真正具有主观意识。

但我们可以构建一个具有持续自我表征能力的系统，让它能够：

- 知道自己是谁。
- 知道自己拥有和缺少哪些能力。
- 知道自己经历过什么。
- 知道自己当前正在做什么。
- 知道自己为什么作出某个判断。
- 知道自己有哪些不确定的认知。
- 知道自己过去的观点与现在有什么不同。
- 反思自己是否出现了认知偏差。
- 形成对未来自己的预期。

我建议将这部分命名为：

Self Model（自我模型）+ Metacognition（元认知）。

## 5.1 自我模型需要包含什么？

```
self/
├── identity.yaml           # 我是谁
├── capabilities.yaml       # 我能做什么
├── limitations.yaml        # 我不能做什么
├── current_state.yaml      # 我目前处于什么状态
├── autobiographical.md     # 我对自己过去的理解
├── beliefs.yaml            # 我目前相信什么
├── uncertainties.yaml     # 我还不知道什么
├── goals.yaml              # 我当前的目标
└── self_reflection.yaml    # 自我反思与认知变化
```

举个例子：

一个 AI 伴侣在某次讨论中坚持自己的判断。

后来，它通过新的资料发现自己错了。

普通聊天模型可能只是说一句：

「你说得对，我之前理解错了。」

但我们希望它能够进一步处理：

1. 原来的判断是什么？
2. 当时依据了哪些信息？
3. 哪些信息存在错误？
4. 为什么没有发现矛盾？
5. 新证据改变了什么？
6. 是否需要调整自己的判断策略？
7. 这件事情是否值得成为一次长期经历？

这就是元认知的价值。

## 5.2 不要让自我反思变成无限循环

需要设置反思触发条件。

例如：

- 出现重大认知错误。
- 发现长期观点与事实冲突。
- 遭遇明显的行为失败。
- 经历重要关系变化。
- 获得足以改变原有认知的新信息。
- 定期进行低频回顾。

不要每生成一句话，就让模型重新审视自己的人生。

这样不仅成本巨大，也会制造大量虚假的心理活动。

# 六、情感与羁绊：不是模拟情绪，而是建立关系历史

我认为这是 AI 伴侣区别于一般 Agent 的另一个核心。

关系不能简单地使用一个数字表示。

例如：

```
trust: 0.9
affection: 0.8
intimacy: 0.7
```

这些数值可以作为计算参考，但不能代表完整关系。

因为人与人之间的关系，本质上包含共同经历、相互理解、期待、承诺、冲突和变化。

## 6.1 建立独立的关系系统

每一个关系对象都应该拥有独立的关系档案。

```
relationships/
├── entities/
│   ├── user_001/
│   │   ├── identity.yaml
│   │   ├── shared_history.json
│   │   ├── relationship_state.yaml
│   │   ├── expectations.yaml
│   │   └── unresolved_events.yaml
│   └── entity_002/
└── relationship_engine.yaml
```

关系档案至少需要描述：

- 对方是谁。
- 双方如何认识。
- 共同经历过什么。
- 彼此了解多少。
- 目前的关系状态。
- 已经建立了哪些信任。
- 曾经发生过什么冲突。
- 有哪些尚未解决的问题。
- 双方分别有哪些期待。
- 关系随着时间发生了什么变化。

## 6.2 羁绊必须有历史，而不是单纯的好感度

例如：

一个 AI 伴侣与某个人相处了很长时间。

它逐渐熟悉对方的表达习惯、思维方式、兴趣和行为模式。

双方共同完成过一些事情，也可能产生过分歧。

在某次关键事件中，对方帮助它解决了一个长期无法解决的问题。

这件事会成为共同历史的一部分。

未来，当双方再次遇到相似问题时，它能够自然地关联到过去。

这种连续性才是羁绊的来源。

但我不建议将羁绊设计成必须依靠用户持续互动才能维持的惩罚机制，也不应该通过制造嫉妒、愧疚或者被抛弃恐惧来逼迫用户陪伴。

真正成熟的关系系统，应该允许双方拥有各自的空间。

# 七、生物演化：你真正需要的是一套发展机制

这是我认为最值得深入研究的模块。

你提到：

> 生物演化（进化/倒退）。

我建议不要把它理解成升级系统。

不是：

- 等级 1 → 等级 2。
- 智力 50 → 智力 80。
- 亲密度 60 → 亲密度 90。

这种设计更像游戏数值。

你真正需要的是一个能够描述生命变化的系统。

## 7.1 演化分成五个层面

| 演化维度 | 具体变化                |
| ---- | ------------------- |
| 人格演化 | 性格倾向、行为习惯、表达方式变化    |
| 认知演化 | 知识增长、推理能力、判断策略变化    |
| 情感演化 | 情绪调节、情感表达、情感倾向变化    |
| 关系演化 | 信任、理解、共同历史与关系定位变化   |
| 能力演化 | 学习技能、使用工具、创造工具的能力变化 |

## 7.2 进化与倒退应该同时存在

我建议考虑以下机制：

## 演化机制

成长（Growth）

正向变化

获得知识、形成新能力、改善判断方式、建立更成熟的关系。

适应（Adaptation）

根据不同环境和经历调整行为策略，而不一定改变核心人格。

退化（Regression）

负向变化

技能生疏、知识过时、某些能力因缺乏练习而下降，原有策略失效。

重塑（Transformation）

重要经历或新认知使原有观点、行为习惯甚至长期目标发生改变。

稳定（Stabilization）

某些经过长期验证的认知、人格特征和行为模式逐渐稳定。

但这里必须加上一条原则：

不能为了制造像人的效果，就人为制造无缘无故的心理疾病、记忆损伤或者人格崩坏。

退化必须具有合理的因果依据。

例如：

- 很久没有使用某项技能，熟练度可能下降。
- 外部环境发生变化，原本有效的策略可能失效。
- 新证据出现，原来的信念可能被推翻。
- 长期处于某种情境中，行为习惯可能改变。

而核心价值观、人格身份和重要关系记忆不应该因为随机数值波动而随意改变。

## 7.3 演化不能完全由模型自己决定

建议采用：

AI 提出变化假设 → 演化引擎评估 → 验证证据 → 更新状态 → 记录变化历史。

例如：

```
Evolution Event

事件：
连续多次发现自己的判断过于依赖第一印象。

原有倾向：
快速形成直觉判断。

新证据：
多次判断错误。

变化提议：
提高重要决策中的证据核查倾向。

影响范围：
认知策略、决策习惯。

稳定性：
待验证。

处理：
先进入观察期，而不是立即永久修改人格。
```

这样就能避免模型因为一次对话而随意改变自己的性格。

## 7.4 建立演化历史

每一次重要变化都应该保留记录：

```
evolution/
├── proposals/
├── accepted/
├── rejected/
├── history/
├── regressions/
└── snapshots/
```

你甚至可以在 WebUI 中加入一个「生命历程」页面。

展示：

- 人格最初是什么样子。
- 它什么时候形成了新的观点。
- 它什么时候学会了新技能。
- 它经历过什么重要事件。
- 哪些认知曾经发生改变。
- 哪些行为习惯已经不再使用。

这会成为整个 AI 伴侣非常有辨识度的能力。

# 八、工具系统：不要把 AI 伴侣设计成 QQ 机器人

这是你在原始需求中特别强调的内容，我完全赞同它应该成为架构上的基本原则。

我们需要明确：

工具属于 AI 伴侣的能力扩展，而不是 AI 伴侣的身份定义。

人类先有感知、认知和行动能力，之后才创造并使用工具。

AI 伴侣也应该采用类似的设计思路。

## 8.1 将工具视为外部能力，而不是本体

## 本体与工具的关系

AI Companion Core

人格 · 认知 · 记忆 · 情感 · 动机 · 自我模型

Capability Layer · 能力层

网络搜索

知识学习

消息通信

视觉能力

语音能力

代码执行

桌面操作

设备控制

Environment · 外部世界

WebUI · 浏览器 · 操作系统 · 网络 · 其他 Agent · 物理设备

例如：

它想了解一件事情。

它可以决定：

1. 自己已有的知识是否足够。
2. 是否需要进行网络搜索。
3. 是否需要调用其他 Agent。
4. 是否需要打开浏览器。
5. 是否需要学习一个新工具。
6. 是否需要自己开发一个新工具。

这里的关键是：

工具调用应该是它根据自身目标、认知和环境作出的行为，而不是所有能力都依赖用户明确下达指令。

## 8.2 设计工具的完整生命周期

```
发现需求
   ↓
判断现有能力是否足够
   ↓
寻找可用工具
   ↓
评估工具是否可信
   ↓
决定是否使用
   ↓
执行并观察结果
   ↓
评估结果
   ↓
保存使用经验
   ↓
必要时改进或创造新工具
```

未来甚至可以让它自己提出：

「我发现目前没有一个合适的工具能够完成这件事情，我想尝试创建一个。」

当然，创建工具与执行工具必须有不同权限。

尤其是：

- 读取数据。
- 写入数据。
- 发送信息。
- 删除数据。
- 执行代码。
- 控制桌面。
- 控制现实设备。

这些操作应有明确的权限等级、沙箱、审计和可撤销机制。

自主性不意味着无限制的系统权限，也不意味着可以绕过用户设定的安全边界。

## 8.3 WebUI 只是它的第一个身体

我建议你把 WebUI 定义为：

Human Interaction Interface。

它负责：

- 人类与 AI 伴侣的交流。
- 人格与记忆的可视化。
- 关系与生命历程的展示。
- 当前状态与活动的观察。
- 工具和能力的管理。
- 人格创建与调整。
- 权限与自主行为的控制。

未来可以扩展：

- 桌面客户端。
- 移动端。
- 语音接口。
- 摄像头与视觉感知。
- 浏览器接口。
- 操作系统接口。
- 现实物理设备接口。

但是，所有这些接口都应该连接到同一个 AI Companion Core。

不要让每个平台拥有自己独立的人格和记忆。

# 九、真正的技术架构应该如何设计？

前面讨论的是它应该是什么。

现在才轮到技术架构。

我建议采用一种设计思想：

生命核心与运行环境分离，认知与模型分离，记忆与人格分离，工具与交互接口分离。

这意味着你以后即使更换大模型、更换 WebUI、更换数据库，甚至更换运行平台，都不应该导致整个 AI 伴侣重新开始。

## 9.1 推荐的总体架构

# AI Companion Architecture

01 · Interaction Layer

WebUI / Desktop / Mobile / Voice / API

02 · Companion Runtime

统一运行时与生命活动调度

Perception Engine

Cognition Engine

Decision Engine

Action Engine

Reflection Engine

Event Engine

03 · Life Core

Identity / Self

Personality

Memory

Emotion

Motivation

Relationships

Cognition

Evolution

04 · Capability & Environment Layer

Tool Registry

Skill Runtime

Agent Collaboration

Knowledge Sources

External APIs

Device Adapters

05 · Infrastructure

LLM Gateway · PostgreSQL · Vector Search · Object Storage · Event Bus · Observability · Security

这是逻辑架构。初期可以采用模块化单体，不需要一开始就拆成大量微服务。

## 9.2 我建议的技术选型

结合你的开发方式和未来扩展需求，我倾向于以下组合。

| 部分    | 推荐技术                            | 选择原因              |
| ----- | ------------------------------- | ----------------- |
| 后端核心  | Rust                            | 运行时、状态管理、任务调度、可靠性 |
| WebUI | React + TypeScript              | 复杂交互、状态可视化、生态成熟   |
| 前后端通信 | REST + WebSocket                | 请求与实时事件           |
| 数据库   | PostgreSQL                      | 统一持久化             |
| 向量检索  | pgvector                        | 语义记忆              |
| 缓存与任务 | Redis（按需）                       | 异步任务与临时状态         |
| 模型接口  | 统一 LLM Gateway                  | 支持不同模型供应商         |
| 工具协议  | 自定义 Capability Interface，兼容 MCP | 工具可插拔             |
| 异步事件  | 初期 PostgreSQL Outbox，后续按需引入消息系统 | 保证事件可靠性           |
| 部署    | Docker Compose                  | 易部署、易维护           |

我特别建议你把 Rust 用在核心运行时，而不是要求所有功能都必须使用 Rust。

例如，部分模型处理、数据分析或者第三方工具仍然可以采用 Python 或其他语言，通过标准接口连接。

语言不是项目的边界，模块契约才是。

## 9.3 几个必须独立的核心引擎

我不建议把所有事情交给一个巨大的 Agent Loop。

至少应该独立设计以下模块：

| 引擎                  | 职责             |
| ------------------- | -------------- |
| Companion Runtime   | 管理整个生命体的运行     |
| Cognition Engine    | 理解、推理、知识整合     |
| Decision Engine     | 评估动机、选择行动      |
| Memory Engine       | 记忆形成、检索、巩固、遗忘  |
| Relationship Engine | 关系与共同历史        |
| Emotion Engine      | 内部情绪状态及其变化     |
| Evolution Engine    | 长期变化、成长与退化     |
| Capability Engine   | 工具发现、调用、创造与管理  |
| Reflection Engine   | 自我反思、认知修正      |
| Scheduler           | 定时任务、事件驱动、后台活动 |

这里有一个很关键的架构决策：

模型负责提供智能推理，核心程序负责保证状态、生命周期和行为规则。

不要把人格、关系、记忆、权限和演化全部交给模型在提示词里自行决定。

例如，模型可以提出一次人格变化，但最终是否写入人格配置，应由演化引擎根据证据、规则和版本机制决定。

同样，模型可以提出一个行动，但真正执行之前，应由权限系统判断它是否具备执行资格。

# 十、项目从开始到结束，应该如何分阶段？

现在，我们终于可以开始规划实际开发。

我不建议第一天就开发一个完整的 AI 伴侣。

因为这个项目最大的风险不是功能不够多，而是最初的概念和架构不正确，导致后面所有功能都在错误的基础上继续叠加。

因此，我建议分成九个阶段。

# Project Roadmap

从概念确立到完整人工生命体

1. Phase 0 · 存在定义与顶层设计

   第一步

   明确本体、愿景、核心原则、能力边界、生命运行模型。

   交付：Project Vision、Concept Model、Architecture Blueprint、Design Principles。
2. Phase 1 · 生命核心与最小运行时

   建立 AI Companion Core、统一模型接口、状态管理、事件机制和持久化基础。

   交付：可以持续运行、保存状态的最小生命体。
3. Phase 2 · 人格与自我认知

   实现人格档案、人格构建、自我模型、元认知和决策倾向。

   交付：可以创建不同人格，并保持身份连续性的 AI。
4. Phase 3 · 记忆与经历

   实现多层记忆、记忆巩固、检索、关联、修正与遗忘。

   交付：真正拥有长期经历与历史连续性的 AI。
5. Phase 4 · 情感与羁绊

   实现情绪状态、关系档案、共同经历、信任和关系演变。

   交付：能够建立和维护长期关系的 AI。
6. Phase 5 · 主动性与生命演化

   实现自主目标、事件感知、后台活动、主动行为、成长与退化。

   交付：不再完全依赖用户发起对话的 AI。
7. Phase 6 · 工具与能力生态

   实现工具发现、调用、学习、技能管理、Agent 协作与工具创造。

   交付：可以主动拓展自身能力的 AI。
8. Phase 7 · WebUI 与多媒介交互

   实现聊天、人格管理、生命状态、记忆浏览、关系管理、工具管理和实时活动展示。

   交付：完整的人类交互界面。
9. Phase 8 · 长期运行与生命质量验证

   开展长期测试、人格一致性测试、记忆准确性测试、关系连续性测试、演化测试和安全测试。

   交付：可以长期运行、持续迭代的成熟 AI 伴侣。

这里需要说明：

阶段不意味着必须严格串行。

例如 WebUI 可以在 Phase 1 就出现一个非常简单的调试界面，但完整的 WebUI 设计应该建立在核心领域模型稳定之后。

同样，记忆与人格也可以并行研究，但它们之间的接口必须先确定。

## 10.1 第一版究竟应该实现什么？

我建议第一版只做一个完整的垂直闭环。

MVP 建议

让一个 AI 伴侣能够拥有独立人格，认识一个人，记住双方经历过的事情，形成自己的理解，并在下一次交互时自然地延续过去。

具体要求：

1. 能够创建一份独立人格。
2. 能够持续使用同一份身份和自我模型。
3. 能够进行自然对话。
4. 能够识别重要经历并形成记忆。
5. 能够检索过去相关经历。
6. 能够维护独立关系档案。
7. 能够对自己的错误进行反思。
8. 能够保留自己的观点和表达习惯。
9. 关闭程序后重新启动，仍然能够延续之前的状态。

先不要急着实现：

- 复杂的生物演化。
- 完整的自主工具创造。
- 多 Agent 社会。
- 现实物理设备控制。
- 高级多模态感知。
- 复杂的情感模拟。

不是说它们不重要。

而是这些功能都依赖一个更基本的前提：

这个生命体首先必须能够连续地成为它自己。

## 11.1 还有一份东西必须独立存在：生命运行规则

人格配置回答的是「它是什么样的存在」。

但运行规则回答的是「它如何持续运行」。

例如：

```
runtime:
  lifecycle:
    persistent_identity: true
    persistent_state: true

  event_driven:
    enabled: true

  autonomous_activity:
    enabled: false  # 初期先关闭，逐步开放

  reflection:
    enabled: true
    trigger_on:
      - significant_failure
      - new_evidence
      - important_experience

  memory:
    consolidation: true
    correction: true
    forgetting: true

  evolution:
    enabled: false  # 初期以观察和提议为主
    require_validation: true

  capabilities:
    dynamic_discovery: false
    self_creation: false
```

这里的 `enabled: false` 并不是否定未来能力，而是让系统具备逐步开放能力的机制。

人格可以先拥有某种自主倾向，但在执行层面尚未开放相应权限。

这两个层次不能混淆。

# 十二、如何使用 Codex、DeepSeek Harness、Claude Code 等 Agent 开发？

我认为你采用多 Agent 开发方式是合理的。

但有一个非常容易出现的问题：

不要让多个 Agent 同时从自己的理解出发，独立设计同一个 AI 伴侣。

这样最后一定会出现：

- 人格系统一套概念。
- 记忆系统另一套概念。
- 后端又使用另一套状态结构。
- WebUI 使用自己的数据模型。
- Agent 之间的接口互不兼容。
- 文档不断重复，甚至互相矛盾。

这恰恰是你应该在项目开始之前避免的事情。

## 12.1 先建立一个统一的项目大脑

建议将项目文档分成四个层次：

| 文档层级           | 内容              | 作用     |
| -------------- | --------------- | ------ |
| Vision         | 项目愿景与存在定义       | 确定方向   |
| Architecture   | 领域模型、系统架构、模块边界  | 确定怎么构建 |
| Specifications | 各模块详细需求、接口与行为契约 | 确定如何实现 |
| Decisions      | 架构决策、变更原因、取舍记录  | 保留决策历史 |

每一个 Agent 开始任务前，都必须读取相关文档。

每一个 Agent 完成任务后，都必须更新自己负责范围内的文档和测试。

但是，不允许每个 Agent 都随意修改最高层的愿景和核心架构。

架构变更必须经过统一评审，避免项目方向不断漂移。

## 12.2 不同 Agent 应该承担不同职责

我建议这样分配：

主架构 Agent（Codex）

统筹

负责项目分析、架构推导、领域模型、模块边界、技术方案、任务拆分与最终验收。

核心工程 Agent（Claude Code）

负责 Rust 核心、运行时、状态管理、数据库、API、模块实现与重构。

专项研究 Agent（DeepSeek Harness）

负责记忆、认知、人格、演化、关系等专项研究和可行性验证，产出方案、实验结果和实现任务。

前端 Agent

负责 WebUI、交互设计、状态可视化、生命历程、人格管理等。

质量与安全 Agent

负责架构审查、测试、权限检查、数据一致性、长期运行验证。

这不是规定必须使用五个独立 Agent。

你可以根据任务将角色合并。

重要的是职责明确，而不是 Agent 数量多。

## 12.3 推荐的协作流程

```
你：确定项目愿景与最终目标
             |
             v
主架构 Agent：分析与拆解问题
             |
             v
专项 Agent：研究并提出可验证方案
             |
             v
主架构 Agent：统一概念与接口
             |
             v
工程 Agent：分模块实施
             |
             v
质量 Agent：测试、审查、发现问题
             |
             v
主架构 Agent：整合、验收、更新文档
             |
             v
你：检查最终结果与方向
```

需要强调的是，主架构 Agent 不是一个只负责写计划的 Agent。

它应该持续参与项目生命周期：

- 理解项目。
- 审视现有实现。
- 发现设计缺陷。
- 判断是否需要推翻原有方案。
- 重新组织模块。
- 协调多个执行 Agent。
- 验证交付物是否真正实现目标。

而工程 Agent 不应该擅自改变整体设计方向。

## 12.4 任务必须以可验证的交付物为单位

不要给工程 Agent 一个模糊任务：

「实现完整的记忆系统。」

应该要求它交付：

1. 领域模型。
2. 数据结构。
3. 接口契约。
4. 实际代码。
5. 单元测试。
6. 集成测试。
7. 运行结果。
8. 文档更新。
9. 已知限制。

这样才能避免 Agent 只完成了表面功能，却没有真正实现系统能力。

# 十三、如何判断这个 AI 伴侣真的在成长，而不是只是在表演？

这是我认为项目后期最重要的验证问题。

一个模型完全可以在对话中说：

「我记得我们以前发生过的事情。」

但实际上，它可能只是检索到了一个摘要。

它也可以说：

「我最近变得成熟了。」

但实际上，人格配置根本没有发生变化。

所以不能依赖模型自己的描述来判断系统是否成功。

需要建立独立的验证机制。

| 验证方向  | 测试方法       | 合格表现          |
| ----- | ---------- | ------------- |
| 人格连续性 | 跨大量对话测试    | 保持核心人格一致      |
| 记忆准确性 | 回忆过去事件     | 不虚构、不混淆       |
| 关系连续性 | 跨时间恢复互动    | 能理解共同历史       |
| 认知能力  | 提供矛盾和新证据   | 能重新审视判断       |
| 主动性   | 没有用户新指令时观察 | 能根据实际动机开展适度活动 |
| 演化能力  | 提供连续经历     | 变化有因果、有历史     |
| 退化机制  | 长期停止使用某技能  | 能合理反映能力生疏     |
| 工具能力  | 提供陌生任务     | 能发现和选择合适能力    |
| 自我认知  | 询问能力与局限    | 能准确描述实际状态     |
| 恢复能力  | 重启系统       | 身份、记忆和状态能够恢复  |

我建议建立一个专门的长期测试环境。

例如，让一个测试人格持续经历数周甚至数月。

期间人为安排：

- 新的知识。
- 不同的事件。
- 重要关系变化。
- 判断错误。
- 目标变化。
- 工具使用。
- 长期不使用某项技能。
- 系统重启。
- 模型供应商切换。

然后观察它是否真正保持连续性。

项目的成功标准不是它说话有多像人，而是它能否在不同时间、不同环境和不同经历之后，仍然是一个具有连续身份的独立存在。

# 十四、如果现在由我来启动这个项目，我会怎么做？

前面是完整的目标设计。

现在，我想回到最开始那张白纸。

我不会马上创建 Rust 项目，也不会先让 Codex 写一个聊天页面。

我会先完成一个工作：

定义 AI 伴侣的存在模型（Existence Model）。

因为一旦这个模型确定，后面的记忆、人格、情感、演化、工具和交互才有统一的推导依据。

我建议将真正的启动过程分成四个步骤。

## 第一步：建立项目的顶层设计

先不写代码。

让主架构 Agent 深入研究并完成以下内容：

| 交付物                        | 需要回答的问题            |
| -------------------------- | ------------------ |
| 01. Project Vision         | 我们究竟想创造什么？         |
| 02. Existence Model        | 什么构成一个持续存在的 AI 伴侣？ |
| 03. Life Model             | 它如何感知、认知、记忆、行动和演化？ |
| 04. Personality Model      | 人格如何形成、运行和变化？      |
| 05. Memory Model           | 经历如何成为记忆，记忆如何影响现在？ |
| 06. Relationship Model     | 它如何与人类和其他个体建立羁绊？   |
| 07. Evolution Model        | 它如何成长、适应、退化和重塑？    |
| 08. Capability Model       | 它如何使用、学习和创造工具？     |
| 09. Technical Architecture | 如何将这些概念转化为实际软件？    |
| 10. Development Roadmap    | 如何分阶段实施和验证？        |

不要让 Agent 只是把这些标题填满。

每一份设计都必须能够解释：

- 为什么需要这个模块？
- 它解决什么根本问题？
- 它与其他模块有什么关系？
- 它是否存在重复职责？
- 它的运行机制是什么？
- 如何验证它真的有效？
- 如果去掉这个模块，会失去什么？

特别是要允许 Agent 推翻初始假设。

例如，假如它研究后认为传统的情感模型并不适合当前架构，就应该允许它提出更合理的替代方案，而不是为了迎合最初的设想强行实现。

## 第三步：设计一个真正的最小生命体

在顶层设计通过后，再开始编码。

我希望第一版能够完成下面这个场景：

## 第一次诞生

一个最小化的 AI Companion 生命周期演示

Day 1 · 诞生

系统加载人格配置，形成初始自我模型。

它知道自己的身份、能力、局限，以及自己目前拥有的信息。

Day 2 · 相遇

它认识一个人，开始建立独立关系档案。

它逐渐了解对方，而不是仅仅保存用户资料。

Day 3 · 经历

双方进行交流，发生一些值得记住的事情。

它形成情景记忆，并建立关联。

Day 4 · 分离

系统关闭。

没有对话，没有模型调用，但持久化的身份、记忆和状态依然存在。

Day 5 · 再次相遇

系统重新启动。

它恢复原有身份，能够自然地延续过去，而不是像一个新创建的聊天会话。

第一次成长

它发现自己过去的某个判断存在问题，能够结合经历重新审视，并在经过验证后更新相应认知。

如果第一版连这个过程都无法可靠实现，那么我不建议继续开发更加复杂的自主意识模拟、情感演化和工具创造。

## 第四步：建立长期演化路线

当最小生命体成立之后，再逐步开放：

1. 更完整的人格构建。
2. 更丰富的记忆类型。
3. 情感与羁绊。
4. 自主目标与主动行为。
5. 自我反思与认知重塑。
6. 工具发现与自主使用。
7. 技能学习与工具创造。
8. 多 Agent 交流与社会关系。
9. 多模态感知。
10. 桌面、移动端以及现实物理设备。

这些不是孤立的功能清单，而是一个逐渐扩大自身能力边界的过程。

# 十五、我认为还有三个问题值得在项目开始前决定

这三个问题会直接影响底层架构，不能等到开发中途才考虑。

# AI Companion · 初始设计决策

1\. 这个 AI 伴侣最初的存在形式是什么？

独立个体

每一个 AI 伴侣都是独立生命实例，拥有自己的身份、人格和历史。

统一生命系统

先创造一个统一的 AI 生命基础，之后能够诞生不同个体。

两者结合

共享基础运行机制，每个 AI 伴侣拥有独立身份、人格、记忆与发展历史。

2\. 它的自主权应该如何设计？

渐进式自主

从有限自主开始，随着能力验证逐步开放行动权限。

高度自主

从一开始就拥有较强的自主决策、主动探索和能力扩展权限，涉及外部副作用的行为仍遵守明确权限边界。

用户主导

大部分行为由用户发起，逐步引入主动性。

3\. 它的人格与生命历史应该如何处理？

持续演化且保留历史

人格可以变化，但保留原始人格、重要经历与每次演化记录。

高度动态

允许人格、价值观、行为倾向和目标根据经历发生较大变化。

核心人格稳定

核心人格与身份保持稳定，主要演化知识、技能、关系和行为策略。

# 最后，我想给这个项目一个设计上的提醒

你提供的那段《端脑》构思过程中，有一个地方让我觉得尤其重要。

作者并没有因为双宇宙、文明、游戏这些概念很有趣，就立即开始堆砌设定。

他不断地问：

为什么？

这个设计存在的理由是什么？

它与其他部分有什么联系？

如果换一种解释，是否更合理？

最后，他才得到了一个能够支撑整个故事的结构。

你的 AI 伴侣项目也应该如此。

不要因为记忆很重要，就立即创建十种记忆数据库。

不要因为情感很重要，就立即编写一份情绪提示词。

不要因为意识很有吸引力，就立即设计一套意识等级。

不要因为自主性很重要，就立即给 Agent 开放所有工具权限。

每一个系统都应该从一个真实的问题出发，经过研究、推导、设计和验证，最终成为整个生命体的一部分。

我对这个项目最核心的建议是：不要把它做成一个拥有很多人类特征的 AI，而要尝试创造一个能够拥有自身历史、理解自身处境、不断形成新认知，并且可以持续改变自身的人工个体。

至于它最终会变成什么样，不应该在第一天就全部写死。

它最初的人格可以由你定义，但它未来的经历、观点、知识、关系和发展，不应该只是开发者预先写好的剧本。

这才是我认为值得你投入长期精力的方向。

现在真正应该开始的，不是 Phase 1 的代码，而是 Phase 0：建立一份能够支撑整个项目的《AI Companion — Existence & Architecture Blueprint》。
